1. EXECUTIVE SUMMARY & APPLICATION PURPOSE
--------------------------------------------------------------------------------
StockiPro (v1.2.0) is a high-performance, multi-tenant Software-as-a-Service (SaaS)
designed specifically for real-time inventory counting, warehouse audits, and stock
discrepancy reconciliation. It bridges the operational gap between frontline warehouse
auditors scanning physical barcodes on shop floors/warehouses and business administrators
supervising inventory variance, discrepancies, and stock ledger synchronization in
real time.

Key Objectives:
- Fast, mobile-first inventory counting using mobile device cameras without expensive
  proprietary barcode terminals.
- Instant duplicate count detection and location collision warnings to prevent double counts.
- Seamless offline resilience via IndexedDB caching when warehouse network connectivity drops.
- Real-time stock variance computation (Physical Count vs System Snapshot) with instant
  Postgres Realtime event broadcasts.
- Robust multi-tenant isolation guaranteeing zero data leakage between different stores/tenants.
- Frictionless worker onboarding using single-use 6-digit setup PINs without exposing real email
  addresses to frontline workers.


2. ARCHITECTURE & SYSTEM DESIGN
--------------------------------------------------------------------------------
StockiPro is engineered using a modern full-stack web architecture leveraging Next.js
(App Router) and Supabase (Postgres, Auth, Realtime, Row-Level Security).

A. Architectural Layers:
1. Presentation & Client Layer (Browser):
   - Next.js 15 Client Components ('use client') optimized for mobile touch and warehouse usage.
   - html5-qrcode engine interfacing directly with browser media stream for low-latency barcode decoding.
   - IndexedDB local queue ('stockipro-offline') providing persistent storage for counts submitted during offline periods.
   - SheetJS (xlsx) for fast client-side parsing and generation of Excel audit files.
   - Realtime Supabase websocket channel listening to 'inventory_logs' change events.

2. Application & Routing Layer (Next.js App Router):
   - Global Edge/Server Middleware ('middleware.ts') providing proactive Route Guarding and Role-Based Access Control (RBAC).
   - Server Actions ('use server') handling business mutations, authorization checks, and database transactions.
   - Two Supabase client instances:
     * Server Client ('lib/supabase/server.ts'): Uses user session cookies, strictly constrained by Supabase Row-Level Security (RLS).
     * Service Role Admin Client ('lib/supabase/admin.ts'): Bypasses RLS strictly on the server for provisioning, PIN management, and system snapshot locking.

3. Database & Security Layer (Supabase / PostgreSQL):
   - PostgreSQL 15+ database schema with custom schemas ('public' and 'private').
   - Row-Level Security (RLS) enabled on all application tables with zero security advisor alerts.
   - Helper security definer functions in 'private' schema ('private.get_user_tenant_id()', 'private.is_master()').
   - Dynamic real-time calculation view: 'public.inventory_discrepancies' configured with 'security_invoker = true'.
   - Unique constraints preventing multiple concurrent active inventory sessions per tenant.

3. CORE MODULES & FUNCTIONALITY
--------------------------------------------------------------------------------
A. Authentication & Multi-Tenancy Engine:
- Zero Email Exposure: Warehouse workers only remember their Store Code, Username, and PIN/Password.
- The system generates an internal RFC-compliant synthetic email:
  '{username}@{tenant_code}.stockipro.internal'.
- Two-Phase Login Flow:
  1. Lookup: Validates that the tenant exists and is active, then checks if the user is active. Determines if the account has a password or needs initial activation.
  2. If 'needs_activation': Worker enters their 6-digit PIN and chooses a new 8+ character password. The bcrypt hash is validated, PIN is cleared, and Supabase Auth credentials are set.
  3. If 'has_password': Standard password authentication via Supabase Auth.
- Account Deactivation Double-Lock:
  Worker deactivation marks 'is_active = false' in 'app_users' (blocking lookup) and sets a ban duration on Supabase Auth ('876000h'), preventing any bypass.

B. Barcode Scanner & Frontline Counting (/scan):
- Camera Barcode Reader: html5-qrcode directly scanning 1D and 2D barcodes.
- Duplicate Detection: As soon as a barcode is scanned or entered, 'lookupBarcode' checks if that item was already counted in the active session. If counted:
  * Visual Warning Card displays previous count, location, timestamp, and who counted it.
  * Worker can switch between 'Create new count' or 'Update/correct existing count' (auditors can only edit their own counts).
- Offline Mode (IndexedDB Queue):
  * When submitting a count without internet connectivity (detected via network TypeError), the record is safely placed into the browser's IndexedDB 'pending_counts' store.
  * UI displays a badge: 'X counts pending upload'.
  * Automatically resyncs and flushes when the browser fires the 'online' event or upon the next successful submission.

C. Inventory Dashboard & Live Discrepancies (/dashboard):
- Session Lifecycle:
  * 'active': Open for counting. Only one active session is allowed per store.
  * 'locked': System snapshot frozen into 'inventory_session_snapshots'. Counts are compared against snapshot quantities.
  * 'completed': Session finalized and closed.
- Real-Time Discrepancy Matrix:
  * Subscribes to PostgreSQL Realtime events on 'inventory_logs'.
  * Dynamically queries the 'inventory_discrepancies' view to show:
    Barcode, Product Name, Category, Location, System Quantity, Counted Quantity, Variance (Écart = Counted - System), and Status badge (Positive/Negative/Zero).
- Excel Management:
  * Template generation: 'Stocki_Inventory_Template.xlsx' with standardized columns.
  * Mass Import: Parses Excel files preserving leading barcode zeros, executing batch upserts of up to 500 records at a time under store RLS.
  * Audit Export: Exports all raw counting logs to Excel with timestamp, auditor name, barcode, and location.

D. Worker Administration (/(admin)/workers):
- Admins can provision new warehouse auditors.
- Generates a 6-digit temporary PIN with a 24-hour expiration window.
- PIN is displayed exactly once on screen.
- Admins can regenerate PINs or toggle worker activation status.

E. Master Super-Admin (/admin):
- Restricted exclusively to users with the 'master' role.
- Tenant Onboarding: Generates 6-character clean alphanumeric store codes (avoiding confusing glyphs 0/O/1/I).
- Tenant Activation/Deactivation: Instantly cuts off store access across all users in that tenant.
- Store Analytics: On-demand telemetry of total products, active sessions, and counting logs.


4. DATABASE SCHEMA & SECURITY POLICIES (RLS)
--------------------------------------------------------------------------------
A. Tables:
- 'tenants': Store organizations (id, name, code, is_active, created_at).
- 'app_users': Multi-tenant user profiles (id -> auth.users.id, tenant_id, role, username, full_name, activation_code_hash, activation_expires_at, activated_at, is_active). Roles: 'master', 'admin', 'auditor'.
- 'products': Store catalog (id, tenant_id, barcode, name, category, default_location, system_quantity, purchase_price, sale_price).
- 'inventory_sessions': Counting sessions (id, tenant_id, title, status, locked_at, completed_at). Constraint: 1 active session per tenant.
- 'inventory_session_snapshots': Frozen catalog snapshot taken at session lock (id, session_id, product_id, system_quantity).
- 'inventory_logs': Physical count events (id, session_id, product_id, barcode, counted_quantity, location, counted_by, counted_at).

B. View:
- 'inventory_discrepancies': Security-invoker view aggregating counted quantities vs system/snapshot quantities to compute real-time variance.

C. Row-Level Security:
- Security Definer Helpers: 'private.get_user_tenant_id()' resolves caller tenant; 'private.is_master()' validates super-admin role.
- Tenant Isolation: Every query on products, sessions, snapshots, and logs is constrained by 'tenant_id = private.get_user_tenant_id()' OR 'private.is_master()'.
- Role Isolation: Auditors can only read/insert logs in active sessions and update their own logs.

4. نماذج البيانات وسياسات الأمان (Database Schema & RLS)
--------------------------------------------------------------------------------

- جدول المنتجات (products): دليل المنتجات الخاص بالمتجر (الباركود، الاسم، التصنيف، الموقع الافتراضي، كمية النظام، أسعار الشراء والبيع).
- جدول جلسات الجرد (inventory_sessions): سجل الجلسات وحالتها وتواريخ الإقفال.
- جدول لقطات الجرد (inventory_session_snapshots): اللقطة المجمدة لكميات النظام وقت قفل الجلسة.
- جدول سجلات الجرد (inventory_logs): كل عملية عد تجري في المستودع (الباركود، الكمية، الموقع، العامل، الوقت).

ب. العرض المخصص (View):
- 'inventory_discrepancies': يحسب الفارق الرياضي (Écart = الكمية المعدودة - كمية النظام) مع تحديد الأصناف المسجلة وتلك التي جردت خارج الكتالوج.

ج. سياسات الأمان على مستوى الصف (RLS):
- عزل تام للمتاجر مبني على هوية المستخدم في الـ JWT.
- منع وصول أي متجر لسجلات أو منتجات متجر آخر مهما كانت المحاولات.
- تحديد صلاحيات المدقق الميداني بحيث تقتصر على المسح وتعديل سجلاته الخاصة فقط أثناء الجلسات النشطة.


5. التقرير الفني وحالة التطبيق الحالية (Technical Rapport)
--------------------------------------------------------------------------------
- حالة قاعدة البيانات: مكتملة تماماً، مستضافة على Supabase ومربوطة بالمشروع، خالية من أي ثغرات أمنية (0 Security Advisor Alerts).
- حالة المنطق البرمجي: جاهز 100% ويغطي مسار المصادقة، والمسح، ومنع التكرار، وحساب الفوارق، وتصدير واستيراد الإكسل.
- واجهة المستخدم: مكتملة وظيفياً وتدعم اللغة العربية واتجاه RTL وتمنع التكبير العشوائي أثناء العمل الميداني، وتحتاج لتطبيق هوية بصرية مخصصة (Branding) قبل الإطلاق التجاري العام.
- الاختبارات: توجد اختبارات وحدة برمجية (Unit Tests) تغطي الدوال الحسابية والمصادقة وكشف أخطاء الشبكة.
